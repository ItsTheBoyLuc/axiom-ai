## 2026-09-29 - npm audit fix (CI)

- **Finding:** `npm audit --audit-level=high` failed with 4 high advisories, all transitive via `prisma@7.10.0` (the CLI, which `@prisma/client` also pulls in): `deepmerge-ts <8` (stack exhaustion on recursive objects, via `@prisma/config`) and `mysql2 <=3.23.0` (credential leak on auth-plugin downgrade; zlib decompression bomb). Not a direct dependency. `npm audit --omit=dev` also flagged them, because `prisma` is installed as a dependency of `@prisma/client`.
- **Reachability:** we use PostgreSQL only and never load the MySQL driver. `deepmerge-ts` only merges our own trusted `prisma.config.ts`. Real-world exposure is very low, but a fix was available so we took it instead of relaxing the audit.
- **Fix:** `overrides` in `package.json` pin `mysql2@^3.24.4` (same major) and `deepmerge-ts@^8.0.2` (major bump). No upstream 7.x release fixes this: `prisma@7.10.0` is the latest 7.x and pins the old versions exactly. `npm audit fix` (without `--force`) could not resolve it, and `--force` would downgrade Prisma to 6.x, which is out of policy (keep ^7).
- **Verified:** `npm audit` reports 0 vulnerabilities. `prisma --version`, `prisma validate` and `prisma generate` all work, and the CLI loads `prisma.config.ts` (the `deepmerge-ts` code path) correctly. Re-verify with `prisma migrate` in Phase 3.
- **Remove the overrides when:** a Prisma 7.x release ships with `deepmerge-ts >=8` and `mysql2 >3.23` itself. Review at the start of Phase 3 and Phase 10, whichever comes first (time limit: 2026-12-31).
- **CI:** `actions/checkout` and `actions/setup-node` bumped to v7 (current majors), which also clears the Node 20 deprecation warning.

## 2026-09-29 - Phase 2 (model directory and profiles)

- **Repository layer:** UI and route handlers depend only on `ModelRepository` (`server/repositories/model-repository.ts`). Phase 2 ships an in-memory demo implementation over a fictional dataset (16 "Sample Model N" records from "Demo Provider A-G", all `isDemo`, `UNVERIFIED`, no source URLs). Phase 3 adds a Prisma implementation and switches `getModelRepository()`. The pure filter/sort/search/facet logic lives in `server/repositories/model-query.ts` so it is unit tested independently of storage.
- **Deliberate data gaps in the demo set** (null context window, undisclosed output prices, no benchmarks, historical prices) exist to exercise every "Not publicly disclosed" / "No verified data" path.
- **URL contract:** multi-select filters are comma-separated (`?category=coding,llm`), lists are sorted so equal queries give equal URLs, defaults are omitted, unknown or malformed values are dropped (never an error), out-of-range pages are clamped. Filter, sort and page changes push history; typing in search replaces it (debounced 250ms).
- **Search semantics:** every whitespace-separated token must match (substring, case- and accent-insensitive) in name, family, provider, description, capabilities or categories; name > family/provider > capability/category > description for relevance. Single-letter tokens over-match by nature; revisit with `pg_trgm`/`tsvector` in Phase 3.
- **Sorting:** no relevance or overall ranking. "Benchmark score" sorts by exactly one user-chosen benchmark using each model's most recent result for it (so a newer independent 74% beats an older provider-reported 78%; results are never averaged). Models without a result sort last and read "No verified data". Undisclosed numeric values (context window) sort last.
- **Facet counts** are computed with the group's own filter removed, so alternatives stay visible while filtering. Every option is listed even at zero.
- **Provider filter:** listed providers plus an "Other" bucket (providers with tier `other`), as the spec asks.
- **Comparison tray** lives in the root layout and persists in `localStorage` (`axiom-compare`, max 4). "Compare" needs 2+ models and links to `/compare?models=a,b` (still the "Not built yet" page until Phase 4). A 5th model is refused visibly (disabled button with a reason), never silently dropped. **Recently viewed** (`axiom-recent`, max 12) is recorded on profile pages and shown on `/models`.
- **Not rendered because not built (no dead UI):** profile "Save" (needs accounts, Phase 9) and "Documentation" (only renders when a documentation URL exists; demo records have none).
- **`/api/v1/models/suggest`** was added ahead of the Phase 3 API for the search box. Zod-validated, spec error envelope, short CDN cache. Redis rate limiting arrives with the rest of the API hardening.
- **Cost estimator rules** (`src/lib/pricing.ts`): current prices only (never historical), per-1M-token unit only, cached input counted separately from input, a missing price makes the result _partial_ (lower bound, clearly flagged) and is never treated as free, mixed currencies are refused, values are rounded at 1e-9 to remove float noise, absurd inputs (>1e12) are rejected.
- **Capabilities matrix** cells come only from benchmark results whose category matches the row; three of the eight rows have no demo benchmark category, so they always read "No verified data".
- **SEO:** `/models` and every demo profile are `noindex` while the data is demo. Profiles have unique title/description, canonical URL, `SoftwareApplication` and `BreadcrumbList` JSON-LD (escaped so data cannot break out of the script tag).
- **Route group `(directory)`:** `loading.tsx` at `/models` also wraps nested `[slug]`, which makes unknown slugs stream as HTTP 200. The directory page, its loading and error files live in `app/models/(directory)/` so profile pages are outside that boundary and unknown models return a real 404.
- **Accessibility decisions:** the filter sidebar is a labelled `<section>` (an `<aside>` inside `<main>` nests landmarks); horizontally scrollable tables are focusable `region`s; select labels are associated by `htmlFor` (a wrapping label made the accessible name include the selected value); `scroll-padding` keeps focused elements clear of the fixed navbar and tray (WCAG 2.2 "focus not obscured"); the section nav derives the active item from scroll position (an IntersectionObserver band highlighted the previous section after anchor clicks).
- **Filter groups:** only Provider and Category start open (all five stacked exceed the sticky panel height); a group with an active selection always starts open.
- **Layout gotchas found by screenshots:** card grids need an explicit `grid-cols-1` (an implicit `auto` track grew to min-content and overflowed at 390px); never combine a base `inline-flex` with `hidden`/`lg:hidden` in one class list (it left the desktop-only "Hide filters" button visible on phones).
- **Test infrastructure:** `gotoReady()` waits for hydration (clicks before it are ignored, which flaked under load); axe scans wait for debounced navigations and animations to finish (results are intentionally dimmed while pending, which blends colours).

## 2026-10-02 - Phase 3a (Prisma schema, REST API, seed pipeline)

- **Integrity lives in the database too:** migration `integrity_constraints` adds CHECK constraints to every factual table: no `sourceUrl` unless status is `UNVERIFIED`/`NOT_PUBLICLY_DISCLOSED`; `OFFICIALLY_VERIFIED`/`INDEPENDENTLY_EVALUATED` need `verifiedAt`; `isDemo` rows can never claim a verified status. Pricing: non-negative, `effectiveTo >= effectiveFrom`, a current price cannot have ended, and a partial unique index allows one current price per model/type/unit (history stays). Prisma cannot model these, so they are raw SQL; `prisma migrate diff` reports no drift.
- **Seed pipeline:** `prisma/seed/data/*.json` (real, sourced) is validated by Zod (`schemas.ts`) and rejected on any rule violation, including `isDemo: true`. Demo fixtures live in `prisma/seed/demo/` and load only with `SEED_DEMO=true` (`npm run db:seed:demo`). Seeding is an idempotent upsert keyed by slug and invalidates the cache afterwards. Cross references use slugs.
- **Repository switch:** `getModelRepository()` now returns the Prisma implementation. The in-memory demo repository moved to `tests/support/` so UI code can never import demo data; unit tests still use it.
- **API:** `/api/v1/*` Route Handlers share one endpoint registry (`server/api/endpoints.ts`); Zod schemas validate input and generate the OpenAPI 3.1 document at `/api/docs/openapi.json` (UI at `/api/docs`), so behaviour and documentation cannot drift. Errors use the spec envelope `{ error: { code, message, details? } }` and are never cached. Query strings are **strict**: unknown keys are a 400 (`INVALID_QUERY`), unlike the page URL contract, which silently drops them. Successful reads carry a strong ETag (304 on match) and `Cache-Control`.
- **Redis cache:** read-through with tag versioning (invalidating a tag is one `INCR`; entries expire on their own TTL, no key scanning). The cache is an optimisation, never a dependency: any Redis error is logged (rate limited) and treated as a miss (`X-Cache: BYPASS`). With `enableOfflineQueue: false` the first requests after a cold start can bypass the cache until the lazy connection is ready; this is intended and visible in logs as `[cache] read failed, bypassing cache`.
- **Build needs no database:** `generateStaticParams` returns `[]` for `/models/[slug]`; profiles render on first request and are cached for an hour (ISR). Verified by building with an unreachable `DATABASE_URL`.
- **Docker fixes found while verifying the full stack:** (1) `npm ci --ignore-scripts` skipped the `postinstall` hook, so the builder now runs `prisma generate` explicitly, and `prisma/generated` is dockerignored so a stale host copy cannot leak in; (2) `tests/` is no longer dockerignored because `playwright.config.ts` imports `tests/support/test-db` and `tsc` checks it during the build (runtime stages copy only what they need, so tests do not ship); (3) a one-shot `migrate` service (`target: migrate`, runs `prisma migrate deploy`) now gates `web` and `worker` via `service_completed_successfully`. Run the real seed in the stack with `docker compose run --rm migrate npm run db:seed`.
- **Test databases:** integration and e2e tests use separate databases (`axiom_test`, `axiom_e2e`) on the dev server and refuse to touch the development database. Playwright's web server runs `tests/e2e/prepare-db.ts` (create, migrate, seed demo, flush cache) before `next start`.
- **Verified 2026-10-02:** migrations apply to an empty database (25 tables, `pg_trgm`); 199 unit, 206 integration and 70 Playwright tests pass; production build, `/api/v1/health`, and the full Docker stack (non-root, all services healthy) work; demo seed is idempotent.
- **Prisma overrides review (due at the start of Phase 3): keep them.** `prisma@7.10.0` is still the newest 7.x (`prev` tag) and still pins `mysql2@3.15.3` and, via `@prisma/config`, `deepmerge-ts@7.1.5`. The only newer line is `8.0.0-rc.19` (a prerelease and a major bump, out of policy). `npm audit` is clean (0 vulnerabilities, with and without `--omit=dev`) and `prisma migrate deploy`/`status`/`diff` work with the overrides. Next review: start of Phase 10, hard limit 2026-12-31.
- **Deferred:** Redis rate limiting for `/api/v1/*` is part of the hardening work (docs/PROMPT.md security list), not Phase 3; the API currently relies on CDN-friendly caching only. Sourced seed data (Phase 3b) and `docs/DATA_STATUS.md` are the remaining Phase 3 work, so the "replace demo data on Phase 1-2 pages" criterion is complete only once real data is loaded.
- **Search race fixed (found by the new CI e2e job):** choosing a suggestion (Enter or click) did not cancel the debounced `?q=` URL update, so on a slow page render the URL fell back to `/models?q=...` right after navigating to the profile. `openModel()` in `search-box.tsx` now cancels the pending update first; two fake-timer unit tests pin it (they fail on the old code). ## 2026-10-03 - Phase 4 (Compare)

- **The URL is the single source of truth** for `/compare?models=a,b,c`. Adding or removing a model calls `router.replace` (no history spam, `scroll: false`) and the server re-renders with the new set, so every state is shareable and survives reload. The comparison tray follows the URL (`replace()` on the tray store) and is hidden on `/compare`, which has its own controls. Malformed or surplus slugs are dropped and reported; unknown slugs are reported with a one-click "remove from the link"; the page never 404s on a bad selection.
- **Pure layer, tested** (`src/lib/compare/`): `values.ts` (formatting shared by the table and the CSV so they cannot disagree), `table.ts` (groups General, Technical, Performance, Pricing, Availability; `differs` per row; benchmark caveat), `charts.ts` (series for each chart and the radar rules), `history.ts`.
- **Benchmarks are never merged.** One row per benchmark, grouped by category, each cell with score, evaluation type, date, model and benchmark version and a source link. When the models' results for one benchmark differ in evaluation type, benchmark version or unit, the row carries a "not directly comparable" warning. "Shared benchmarks only" hides rows that only one model has (real overlap between models is sparse).
- **Radar rule (spec: "only shared, explicitly normalized scale").** An axis qualifies only if every selected model has a result, the unit is `%` (an intrinsic 0-100 scale, so nothing is rescaled), scores are within 0-100, and all results share one evaluation type and benchmark version. Fewer than 3 qualifying axes: no radar, the reason is shown. More than 8: the first 8 alphabetically are drawn and the note says how many qualified. Series are told apart by colour, marker shape and dash pattern. No averaging, no weights.
- **Honest charts.** A model without a value (context window, price, benchmark) is named under the chart as not shown, never drawn as zero. Price charts use the same single-unit rule as the estimator and the card (`estimatorUnit`): models with tiers are omitted and named; mixed currencies are never charted. Each chart has units, a source/method note, a table view and a CSV download (shared `charts/download.ts`).
- **CSV export fixed for real data.** `server/api/compare-csv.ts` priced only the plain `per 1M tokens` unit, so models with qualified units (tiers, deployment types) exported "Not publicly disclosed" for a price that exists. It now lists every current variant with its unit (shared `priceLines`). Regression-tested.
- **Selector.** Instant search with provider and category filters through the existing `/api/v1/models` (debounced, aborts stale requests), recently viewed, and comparison history (localStorage, 8 sets, clearable). It starts open while fewer than two models are selected and collapsed after, so the table is not pushed off-screen on phones.
- **Save to account is not rendered** (CLAUDE.md rule 4: no dead UI). It arrives with Phase 9 (auth); history and the recently viewed list work anonymously now.
- **SEO.** `/compare` without a selection is indexable with a canonical URL; a specific selection is `noindex, follow` (an unbounded set of URLs, meant to be shared, not indexed).
- **Found with real data and fixed on the way:** the homepage comparison preview hard-coded "Demo values for layout testing" under its chart and "demo models" in the table caption; both now depend on `isDemo`.

## 2026-10-03 - Phase 5 (Benchmarks)

- **`/benchmarks` is index + detail, with the URL as the state** (`category`, `benchmark`, `provider`, `family`, `version`, `type`, `from`, `to`; tolerant parser, malformed values dropped, inverted date ranges swapped). The index groups the 59 benchmarks by category and shows, per card, results, models, units, latest date and the evaluation-type mix. The detail view is per benchmark because scores of different benchmarks, versions and evaluation types must never share an axis.
- **Categories use the existing controlled vocabulary** (12 keys, `BENCHMARK_CATEGORIES`), a superset of the spec's list (general knowledge, mathematics, coding, logical reasoning, multimodal, instruction following, long context): "reasoning" and "science" cover the first and fourth, and tool use, computer use, browsing, professional work and creative writing exist because real benchmarks need them.
- **Honest about the evaluation type.** Every result is shown with an `EvaluationBadge` (icon + label). The overview prints how many results are independently evaluated even when that is zero, with a plain-language note: today all 150 results are provider reported. Where a selection is provider-reported only, the detail view says so.
- **Charts, and what they refuse to do.** Latest result per model (ordered by provider and name, never by score), scores over time (one line per model family; single-result families are single markers; needs two distinct dates), score distribution (needs at least 5 models), and a provider dot plot (every model's latest result in a row per provider; needs two providers). Where there is too little data a note says why instead of a chart. **No "best per provider" or any aggregate**: benchmarks carry no "higher is better" flag, so no direction of better is assumed and nothing is averaged or ranked. If one benchmark has several score units, the charts use the most common one and name the rest.
- **Aggregates in the database.** `BenchmarkSummary` gained `modelCount`, `latestDate`, `byType` and `units` (additive API change, grouped queries instead of loading results). An integration test checks each benchmark's aggregates against its own results.
- **Filters are applied in memory** to one benchmark's results (`filterRows`, pure and tested; the REST endpoint supports the same filters server-side). The loader pages through up to 500 results (100 per page) and says when it truncates; real benchmarks have at most 11.
- **Shared chart plumbing:** `ChartFrame` (title, units, table/chart switch, CSV, source note) and `series-style` (colour + dash + marker triples, six distinct) are used by the new charts and the radar. `BarChart` got a `uniform` option so a single series is one colour.
- **Real-data finding:** the data is sparse (median 2 results per benchmark, max 11) and entirely provider reported. The explorer is built for that: counts on every card, "too little data" notes instead of empty charts, and the independent count always visible.

## 2026-10-03 - Phase 8 (Admin): authentication core

- **Deviation from the "Auth.js v5" lock (needs your review).** The admin area needs sessions now (Phase 8), and the Auth.js v5 beta has had breaking changes, offers little for a credentials-only flow (its credentials provider does not support database sessions out of the box) and would add a dependency whose behaviour I would have to work around. I built a small, tested session layer on the same Prisma tables the spec already defines (`User`, `Session`) instead, keeping the spec's properties: Argon2id hashing, DB sessions, USER/ADMIN roles, optional GitHub later. Phase 9 builds sign-up, personalization and the optional GitHub sign-in on top of this core. If you prefer Auth.js, only `server/auth/*` and `src/proxy.ts` change; the admin code depends on `authorize(...)` alone.
- **Passwords:** `@node-rs/argon2` Argon2id with the OWASP minimum parameters (m=19456 KiB, t=2, p=1), transparent rehash when parameters change, a dummy hash is spent for unknown emails so response time does not reveal which accounts exist. Minimum 12 characters, no composition rules (NIST 800-63B), common and email-derived passwords refused.
- **Sessions:** a random 256-bit token in an HttpOnly, SameSite=Lax cookie (`__Host-` prefixed and Secure when served over HTTPS); only its SHA-256 is stored, so a database leak does not yield usable sessions. 7-day lifetime, sliding refresh after 1 day, sign-out and role changes delete sessions server-side.
- **Sign-in hardening:** uniform "invalid email or password" with a uniform 401, fixed-window rate limits per IP (30 per 15 min) and per account (8 per 15 min) in Redis with an in-memory fallback, same-origin (CSRF) check on every state-changing route (Origin, then Sec-Fetch-Site), `next` redirect restricted to same-site relative paths (CRLF, backslash, `//` and absolute URLs refused), request bodies size-limited and strictly validated.
- **Admin routes authorize twice:** `src/proxy.ts` only redirects visitors without a session cookie to `/sign-in` (optimistic, cookie presence only, as the Next.js 16 docs advise); every admin page and route handler then verifies the session and role against the database (`requireAdminPage`, `authorize`). Non-admins get 404 on pages (the experimental `forbidden()` is not enabled) and 403 from the API; unauthenticated requests get 401.
- **First admin:** `npm run admin:create -- --email you@example.com` creates or rotates the admin and writes a random 24-character password only to `.admin-credentials.local` (git-ignored; the script refuses to run if it is not ignored). The password is never printed or logged; the audit log records the event without it.
- **Admin edits reuse the seed pipeline.** An admin record is a seed record, validated by the same Zod schemas and written by the same loader (`override: true` = explicit approval, trust guard skipped), so the data-integrity rules hold for seeds, admin edits and approved imports alike. `collectedAt` is set by the server and `isDemo` is forced to false (demo data cannot be entered through the admin). The audit entry (actor, IP, before, after; secrets redacted) commits in the same transaction. Slugs and article URLs are immutable; changing another natural key (e.g. a price's effective date) replaces the row in one transaction; a second current price for the same model, type and unit is refused with an explanation instead of a database error.

## 2026-10-03 - Phase 8 (Admin): record editor, users, audit log, data sync

- **One schema for every write.** An admin record is a seed record (`prisma/seed/schemas.ts`), so seed files, admin edits and approved imports are validated by the same Zod schemas and written by the same loader. Field lists for the editor (`src/lib/admin/fields.ts`) are checked against those schemas by a unit test (every schema field has exactly one editor field), which already caught four missing yes/no/unknown fields while writing it. The server owns `collectedAt` and forces `isDemo=false`; slugs and article URLs are immutable; a changed natural key (a price's effective date) replaces the row in one transaction; a second current price for the same model, type and unit is refused with an explanation. Deleting a provider that still has models is refused (409).
- **Every admin route goes through `adminRoute`:** session -> ADMIN role (401/403, read from the database on every call, so a demotion applies at once) -> same-origin check on writes -> per-admin rate limit (600 reads and 120 writes per minute) -> handler -> no-store JSON. A test enumerates every `route.ts` under `/api/v1/admin` and fails if one exports a handler that is not wrapped. RBAC is tested for every endpoint (anonymous 401, user 403, admin allowed, forged/expired session 401, CSRF 403) in an integration matrix and again end to end in Playwright.
- **Admin pages** re-check the session themselves (the layout does not re-render on client navigation); non-admins get 404. Profile pages are statically regenerated (`revalidate = 3600`), so an admin write also calls `revalidatePath` for `/models/[slug]` and `/providers/[slug]` in addition to invalidating the Redis cache tags: an edit shows up on the public page at once, which an e2e test pins.
- **Users:** role change, sign out everywhere, delete. Nobody changes or deletes their own account in the UI, and the last administrator can never be demoted or deleted (checked inside the transaction too). Password hashes are never returned. First admin stays `npm run admin:create`.
- **Audit log:** actor, action, record, IP, before and after, written in the same transaction as the change; viewer with filters and expandable values. Secrets are redacted.
- **Data sync, designed to be boring and safe:**
  - _Sources_ are rows (`SyncSource`): adapter kind, JSON config validated by the adapter's own schema, a schedule (`manual` or `every 15m..30d`, nothing more frequent than 15 minutes), enable/disable. No source URLs are seeded: I will not invent feeds from memory, so the dashboard starts empty and shows an example config per type.
  - _Adapters_ (`server/adapters`): `rss` (RSS 2.0 and Atom), `github-releases` (public GitHub API, optional `GITHUB_TOKEN` for the rate limit) and `huggingface` (public API: "repository published by organisation X"). The GitHub and Hugging Face response shapes were checked against the live APIs once, and the fixtures mirror them. Adapters never write: they return seed-shaped candidates.
  - _Polite and defensive HTTP client_ (the only way adapters reach the network): robots.txt honoured per origin and re-checked on every redirect hop (404 = allow, 5xx or unreachable = disallow, Crawl-delay respected), at least 1 s between requests to a host, 10 s timeout, 2 MB cap, manual redirects (max 3), https only, default port only, no credentials in URLs, and an SSRF guard that refuses localhost, private, link-local, CGNAT and multicast addresses (also after DNS resolution and on redirects). Known limit: DNS is resolved by the guard and again by `fetch`, so a hostile resolver could answer differently; DEPLOYMENT.md (Phase 10) recommends an egress firewall for the worker.
  - _Pipeline_ (`server/jobs/sync-run.ts`): fetch, validate every candidate with the seed schemas, diff against the stored record, stage as `ImportedRecord` PENDING. Invalid candidates become `SyncIssue` rows (run = PARTIAL); an adapter failure is a FAILED run with the reason. One run per source at a time; a RUNNING run older than 15 minutes is closed as interrupted. Identical imports are never staged twice (payload hash), including ones an admin already rejected.
  - _Existing records:_ an import never overwrites curated fields (news: summary, related models, category, source classification; releases: kind, model, description, docs link). Only source-owned fields can change, and a re-import that changes nothing is silent. `dataType` and `verifiedAt` alone never count as a change.
  - _Excerpts:_ RSS summaries are cut to at most 200 characters (a syndication-sized snippet with the link, not the article), `isAiSummary=false`, and the admin sees the text in the staging view before approving. Items without a description get a plain "Publisher: title" line rather than an invented summary. Atom entries with only an `updated` date are marked `dateIsUpdated` (the DataCamp lesson).
  - _Approval:_ approve publishes through the loader inside one transaction that also claims the import (a double approve, or approve racing reject, rolls back with 409; tested with two simultaneous approvals). The **trust guard** is checked before the write: an import that would lower the trust of stored data is refused with `TRUST_GUARD` unless the admin passes `override: true`, which in the UI is a checkbox that must be ticked on purpose; the override is audited as `import.approve-override`. Staged payloads are re-validated at approval (a model deleted in the meantime gives 400, not a broken row).
  - _Worker:_ a scheduler tick every 30 s enqueues due sources on the BullMQ `sync` queue (job id stable until the source has run, so a slow run is never queued twice), writes a heartbeat the dashboard reads ("worker online"), and processes with concurrency 2 and no automatic retries (the next schedule is the retry). "Run now" enqueues a job (503 with a clear message when Redis is down; disabled sources cannot be run). The worker image now ships `prisma/` (generated client, seed schemas) and `src/types`; I built it and loaded the sync modules inside the container.
  - _Tests:_ network is never touched (scripted `fetch`); unit tests for schedule parsing, robots.txt, the SSRF guard, the HTTP client and each adapter; integration tests for the pipeline, trust guard, concurrency and source management; Playwright for the dashboard, run detail, imports list/detail, the approve/reject/override flows and the source lifecycle.
- **E2E accounts:** `prepare-db.ts` creates `admin@e2e.test` and `user@e2e.test` with random per-run passwords written to the git-ignored `.e2e-credentials.local`; global setup signs both in once (storage state in `.e2e-auth/`), so no spec spends the sign-in rate limit. The specs that create or delete records run in a second Playwright project after everything else, so a transient record can never disturb the count-based public-page specs.

## 2026-10-05 - Phase 9 (Accounts and personalization)

- **Sign-up** (`/sign-up`, `POST /api/v1/auth/sign-up`) always creates a USER (nobody becomes an admin by signing up; tested). Password rules are the same function on client and server. Limits: 10 sign-ups per address per hour and 500 per hour overall (Redis, in-memory fallback). The Argon2 hash is computed before the email lookup so a taken and a free address cost the same time. **Trade-off, stated plainly:** a duplicate email answers 409 `EMAIL_TAKEN`, which reveals that an account exists. Hiding that needs email delivery (a "check your inbox" flow), which needs outgoing-mail credentials; see `docs/SECURITY.md`. Sign-in stays uniform.
- **No email verification and no password reset yet**, for the same reason (no mail credentials; I will not ask for them in chat). Documented as known limitations. Password change (current password required, other sessions revoked) and account deletion (password required) exist.
- **Optional GitHub sign-in: skipped.** It needs an OAuth app's client id and secret created by the owner. Not rendered (no dead UI). The `Account` table stays in the schema for when it is added.
- **One guard for every session-bound route.** `server/auth/guard.ts` (`guardedRoute`) is the shared wrapper (session, role from the database, same-origin on writes, per-user rate limit, no-store JSON). `adminRoute` and the new `meRoute` are thin wrappers, so `/api/v1/me/*` has the same properties as admin; every query is scoped to `ctx.user.id`.
- **Session chrome:** `GET /api/v1/auth/session` answers 200 with `user: null` for anonymous visitors (no failed requests in the console) and does no database work without a cookie. Navbar shows "Sign in" or the account menu; the menu is non-modal so the rest of the page is not aria-hidden while it is open.
- **Personalization:** saved models, saved comparisons (from the Save button on `/compare`, which needs 2 to 4 models and renders "Sign in to save" for anonymous visitors), recently viewed (anonymous history stays in localStorage; signed-in views are recorded server-side), preferences (theme, preferred providers validated against real provider slugs, "For you" on/off) and a "For you" section on the home page that only renders for signed-in people who have not switched it off. Anonymous parity: every public page works without an account (Playwright asserts no failed requests when signed out).

## 2026-10-05 - Phase 10 (Production readiness)

- **Security review of the custom auth** is in `docs/SECURITY.md` (findings, fixes, known limitations). Changes made because of it: session rotation on sign-in and sign-up, the cookie slides with the server-side session, the audit log no longer keeps a deleted person's email or address, and `admin:create` proves its output file is writable before it creates anything (it created an administrator and then lost the password inside a container).
- **Nonce-based CSP, so every page renders per request.** The policy has no `unsafe-inline` or `unsafe-eval` for scripts. A nonce can only be applied while rendering, so the root layout reads the request headers, which makes the whole tree dynamic: profile pages lost their hourly static regeneration (`revalidate`, `generateStaticParams`) and the admin `revalidatePath` calls were removed because there is nothing static left to revalidate. Data reads stay cached in Redis, and measured server response time on the profile page is 50 to 100 ms. The alternative (Next's experimental SRI hashes) was rejected as experimental. The one concession is `style-src-attr 'unsafe-inline'` for React's `style=""` attributes. Two libraries needed accommodating: Radix's scroll-lock `<style>` gets the nonce through `get-nonce` (`CspNonce`), and Zod's `new Function` probe is disabled in the browser (`zod-browser.ts`). `get-nonce` is now a direct dependency (it was already installed transitively).
- **Redis rate limiting for the public API:** 240 requests per minute per client address, `RateLimit-*` headers, `429` with `Retry-After`, `API_RATE_LIMIT_PER_MINUTE=0` disables it (the e2e server sets 0 because every spec shares one address; the 429 behaviour is covered by integration tests). The site itself reads through repositories, so only external callers and search-as-you-type count.
- **Least-privilege database role.** Web and worker connect as `axiom_app` (no DDL, no TRUNCATE); only the one-shot `migrate` service uses the owner. Created by `docker/initdb/01-app-role.sh` on first start and re-runnable on an existing volume. Containers also drop all capabilities, are read-only and cannot gain privileges; ports are bound to loopback by default (`WEB_BIND`). `AUTH_SECRET` was removed: sessions are random tokens, nothing signs with a secret (it was a leftover from the Auth.js plan).
- **Core Web Vitals fixes (found by measuring, see PROGRESS.md):** the page template and the scroll reveals rendered all content at `opacity: 0` until JavaScript hydrated, so Largest Contentful Paint equalled hydration time (4 to 5 s on a throttled phone). Server HTML is now visible as sent: the first load is not animated, reveals below the fold are armed after hydration, and the hero headline and lead only rise. `/models` also stopped shipping Zod to the browser (about 90 kB gzipped saved) by validating its URL params with plain code. Details and the tunable values: `docs/MOTION.md`.
- **SEO:** `/models` was `noindex` (a Phase 2 leftover for demo data). It is now indexable; filtered, searched, sorted and paged variants are `noindex` with a canonical to `/models`. `robots.txt` and a database-generated `sitemap.xml` were added (no `lastmod`: there is no page-level change time and an invented one would mislead crawlers).
- **The seven "not built yet" placeholder pages are now real:** About, Data methodology (live status counts), Sources (live list of source websites generated from the data, `sources` repository), Contact (`CONTACT_EMAIL`), Privacy, Terms and Cookies. The privacy and cookie texts describe what the software actually stores; a unit test fails if the code uses a browser storage key that `/cookies` does not list, or sets a cookie other than the session cookie. They are not legal advice and say the operator must adapt them. The `[slug]` placeholder route and `pendingRoutes` are gone.
- **Strict `npm audit` gate: not restored.** `braces` 3.0.3 (the affected, dev-only chain through `eslint-config-next`) is still the latest release and the Prisma 7.x line still pins the vulnerable `mysql2` and `deepmerge-ts`, so the production-only blocking gate and the informational full audit stay, and the Prisma overrides stay (review again before 2026-12-31).
- **Docker in CI:** a job builds the three images, boots the Compose stack as in production, seeds, checks non-root, read-only, the app role cannot create tables and the CSP header, then takes a backup and runs the restore test.
- **Backups:** `scripts/ops/` (`pg_dump` custom format, verified and checksummed, retention; restore test into a scratch database; destructive restore with `--yes`). Run end to end on 2026-10-05.
- **Not done:** email verification, password reset, MFA, GitHub sign-in, an absolute session lifetime, image vulnerability scanning in CI (all in `docs/SECURITY.md` under known limitations).
